# V2.7.4 实施路线、任务拆解与验收标准

状态：Planning Draft

更新时间：2026-04-17

## 1. 版本验收目标

V2.7 完成时，系统应满足以下结果：

- 三层记忆有统一 schema 视图
- 写入结果带类型、来源、置信度、状态
- 任务结束后能形成结构化摘要
- 召回默认经过 lifecycle / privacy guard
- 召回结果可解释
- 被替代、被遗忘、已归档、待审核内容不会继续污染默认召回
- 用户或维护者能进行基础治理和查看审计

## 2. 里程碑设计

| 里程碑 | 目标 | 结果 |
|---|---|---|
| M1 | 统一 schema 与记录视图 | 三层对象可映射到统一 record |
| M2 | 理解与压缩基线 | 基础分类、任务摘要、多粒度 summary |
| M3 | 召回与解释基线 | recall guard、budget、explanation |
| M4 | 演进与治理基线 | supersede、conflict、forget、audit |
| M5 | 文档、测试与回归收口 | API/CLI/MCP 文档、集成测试、验收脚本 |

## 5. 测试策略

### 5.1 单元测试

重点覆盖：

- 三层对象到统一 record 的映射
- 类型、来源、置信度、状态推断
- task summary 模板保真
- recall guard 过滤
- supersede / conflict 标记
- soft forget / restore
- audit event 生成

### 5.2 集成测试

重点覆盖：

- `AgentContext -> Summary -> Memory`
- `ProjectDocument -> Record -> Recall`
- `Memory conflict -> needs_review -> recall excluded`
- `Memory supersede -> old deprecated -> new active`
- `soft forget -> default recall excluded`
- `recall explanation` 返回完整原因

### 5.3 回归测试

V2.7 必须保证：

- 不破坏 V2.4 的 context/docs 主链路
- 不破坏 V2.6 的项目边界确认
- 不破坏现有 remember/search/publish/promote 流程

## 6. 验收指标

| 指标 | 目标 |
|---|---|
| Schema 完整率 | 短期、中期、长期对象都可映射到统一 record |
| Summary 保真率 | 任务摘要保留目标、约束、决策、待办 |
| Recall 噪音率 | 默认召回的明显无关项下降 |
| Recall 可解释性 | 主要召回结果都包含 reason 与 score |
| Conflict 标记率 | 明显冲突的高价值记忆能被标记 |
| Forget 生效率 | forgotten 内容不再默认召回 |
| Governance 可控性 | 用户可 archive / forget / restore / inspect |

## 7. 风险与控制

| 风险 | 说明 | 控制方式 |
|---|---|---|
| 设计过大 | V2.7 可能变成 V3 重写 | 先做统一视图，不强推全量迁移 |
| 自动化误判 | 分类、冲突、替代判断不稳定 | 用保守策略，先标记后人工确认 |
| 召回退化 | 新过滤规则可能让 recall 过少 | 先做 explanation 和 metrics，边调边收口 |
| 文档与实现脱节 | 方案写得很大但落地无序 | 所有能力都绑定任务编号和验收标准 |

## 8. V2.7 完成后的版本位置

V2.7 完成后，项目的定位会从：

“支持长期记忆、短期上下文和项目文档的记忆内核”

升级为：

“具备三层记忆、统一生命周期、可解释召回和可控治理的协作记忆系统”

这才是进入 V3 多模态之前更稳的工程状态。
