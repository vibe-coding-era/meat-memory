# V2.7 接入面一致性对比

状态：Implemented

更新时间：2026-04-20

## 1. 对比目标

本文件对比 V2.7 之后 `MCP`、`CLI`、`HTTP API`、`TUI` 四类入口的能力、参数和使用边界，目标是确认生命周期系统不是只在单一入口可用，而是能被 Agent、脚本、服务端和本地操作者一致地使用。

结论摘要：

- V2.7 生命周期主链路已经在 `MCP / CLI / HTTP API` 三个入口保持一致：inspect、status、forget、restore、report 均可用。
- 短期上下文和项目文档同步主链路在 `MCP / CLI / HTTP API` 三个入口基本一致。
- `TUI` 是本地初始化和 operator 向导入口，不追求与 Agent 工具面一一对齐。
- 仍有少量能力差异需要保留或后续补齐，尤其是直接 memory promote/publish、docs import/projection、audit 查询和图片记忆。

## 3. 参数一致性

### 3.1 认证参数

| 入口 | 传递方式 | 判断 |
|---|---|---|
| MCP | tool JSON 参数 `key` | Agent 可显式传 key |
| CLI | `--key` 或 `MEAT_MEMORY_KEY` | 脚本和本地使用均可 |
| HTTP API | `X-Meat-Memory-Key` 或 `Authorization: Bearer` | 服务端标准鉴权方式 |
| TUI | 创建或写出本地 key 配置 | 用于 bootstrap，不作为每次请求参数 |

结论：认证语义一致，但传递位置符合各入口习惯；不建议强行统一成同一字段名。

### 3.2 scope 参数

| 入口 | 表达方式 | 判断 |
|---|---|---|
| MCP | `scope_id` 可选，缺省使用服务默认 scope 或 key owner scope | 一致 |
| CLI | `--scope-id` 可选，缺省使用服务默认 scope 或 key owner scope | 一致 |
| HTTP API | 部分资源通过 path `{scope_id}`，部分通过 request body/query | API 更显式 |
| TUI | 初始化时建立项目 scope/key 绑定 | bootstrap 语义，不参与日常调用 |

结论：MCP/CLI 更适合 Agent 的“少参数默认值”，HTTP API 更适合服务端显式路径。

### 3.3 内容输入参数

| 能力 | MCP | CLI | HTTP API | 判断 |
|---|---|---|---|---|
| 文本 body | `body` | `--body`、`--file`、stdin | JSON `body` | CLI 多本地文件便利能力 |
| 图片 | 不提供 | `--file`、`--media-type` | base64 `image_base64`、`media_type` | MCP 暂缺 |
| Docs import | 不提供 | `--body`、`--file` | `content_text` | MCP 暂缺 |
| Docs sync | `source_id`、`local_root`、`dry_run` | `--source-id`、`--local-root`、`--dry-run` | JSON body | 一致 |

结论：CLI 拥有文件路径和 stdin 是合理增强；MCP 使用 JSON-only 更适合 Agent 调用；HTTP API 使用 JSON/base64 是服务端边界。

### 3.4 生命周期参数

| 操作 | MCP | CLI | HTTP API | 判断 |
|---|---|---|---|---|
| inspect | `memory_id`，可选 `scope_id/query/key` | `--memory-id`，可选 `--scope-id/--query/--key` | path `{scope_id}/{memory_id}`，query `query` | 一致 |
| status | `memory_id/status/reason/actor` | `--memory-id --status --reason --actor` | path + JSON `status/reason/actor` | 一致 |
| forget | `memory_id/reason/actor` | `--memory-id --reason --actor` | path + JSON `reason/actor` | 一致 |
| restore | `memory_id/reason/actor` | `--memory-id --reason --actor` | path + JSON `reason/actor` | 一致 |
| report | `scope_id/limit` | `--scope-id --limit` | query `scope_id/limit` | 一致 |

结论：V2.7 governance 主链路已达成入口一致。

## 5. 差异处理建议

| 优先级 | 建议 | 原因 |
|---|---|---|
| P0 | 保持生命周期 inspect/status/forget/restore/report 在 MCP/CLI/API 三面一致 | 这是 V2.7 的治理主链路，不能退化 |
| P1 | 为 CLI 增加直接 memory publish/promote 命令，或明确记录“只允许 MCP/API 执行跨 scope promote” | 当前 MCP/API 有直接 promote，CLI 缺直接命令，operator 排障会不方便 |
| P1 | 判断 `docs import/projection` 是否要暴露为 MCP tool | 如果 Agent 需要主动导入文档，应补 MCP；如果只允许 operator 管理，应在文档中写明 |
| P1 | 为 MCP/CLI 补 lifecycle audit 查询，或明确 audit 是 API-only 运维面 | V2.7 强调可审计，查询入口最好不只留在 HTTP |
| P2 | 图片记忆 MCP 工具留到 V3 多模态入口统一处理 | 当前 V2.7 不进入全多模态，避免把 MCP 工具面提前扩散 |
| P2 | key/source 管理保持 API/CLI/TUI-only | 这是 provisioning 和 operator 能力，不建议默认交给 Agent 工具 |

## 6. V2.7 一致性边界

V2.7 不要求四类入口完全同形，而要求“同一角色的入口能力一致”：

- Agent runtime：优先 MCP，需要覆盖记忆写入、召回、生命周期治理、短期上下文和文档同步。
- Local operator：优先 CLI/TUI，需要覆盖初始化、key/source/project 管理、诊断、治理和验收。
- Service integration：优先 HTTP API，需要覆盖全部资源和运维接口。
- Bootstrap flow：优先 TUI，不参与每个 runtime 能力的一一对齐。

因此当前最重要的判断不是“每个入口是否完全一样”，而是：

- V2.7 生命周期治理主链路已经一致。
- operator-only 能力需要被明确标注，而不是被误认为缺失。
- 真正影响 Agent 或治理闭环的缺口，应进入后续 P1 队列。
