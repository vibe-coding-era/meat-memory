# V2.7.2 生命周期模型与统一 Schema 设计

状态：Planning Draft

更新时间：2026-04-17

## 1. 设计目标

V2.7 的 schema 目标不是替换三层记忆，而是为三层记忆建立统一描述语言。

需要统一回答这些问题：

- 这条记忆属于哪一层
- 它是什么类型
- 它从哪里来
- 它是否可信
- 它当前处于什么生命周期状态
- 它应该如何参与召回和治理

## 2. 统一模型思路

### 2.1 三层对象继续保留

| 当前对象 | 保留方式 | V2.7 角色 |
|---|---|---|
| `AgentContext` | 保留 | 短期层原生对象 |
| `ProjectDocument` | 保留 | 中期层原生对象 |
| `Memory` | 保留 | 长期层原生对象 |

### 2.2 新增统一视图层

V2.7 建议引入一个统一概念：

`Memory Record`

它不是强制替换底层表，而是统一暴露给：

- recall
- governance
- audit
- explanation
- report

的标准视图。

## 3. 建议的统一字段

| 字段 | 说明 | 来源 |
|---|---|---|
| `record_id` | 统一记录 id | 运行时生成或映射 |
| `native_id` | 原始对象 id | context/document/memory id |
| `layer` | `short_term` / `mid_term` / `long_term` | 直接映射 |
| `scope_id` | 作用域 | 原始对象字段 |
| `record_type` | 统一类型 | 由规则或分类器生成 |
| `title` | 标题 | 原始对象字段 |
| `content` | 主体内容 | 原始对象字段 |
| `summary` | 摘要 | 压缩服务生成 |
| `source_kind` | 来源类型 | conversation/file/api/meeting/manual/system |
| `source_ref` | 来源引用 | thread/file/source/document 等 |
| `confidence` | explicit/inferred/unverified/stale | 理解管线给出 |
| `status` | active/archived/deprecated/forgotten/needs_review | 生命周期状态 |
| `visibility` | 可见性 | 已有字段或映射 |
| `sensitivity` | 敏感等级 | 已有字段或映射 |
| `importance` | 重要性分数 | score / 规则 |
| `freshness` | 新鲜度分数 | score / 规则 |
| `stability` | 稳定性分数 | score / 规则 |
| `expires_at` | 到期时间 | context/task/document 场景可选 |
| `supersedes` | 替代关系 | 演进服务生成 |
| `conflicts_with` | 冲突关系 | 冲突服务生成 |
| `evidence_refs` | 来源证据 | artifact / document / message 引用 |
| `created_at` | 创建时间 | 原始对象字段 |
| `updated_at` | 更新时间 | 原始对象字段 |

## 4. 统一类型设计

### 4.1 record_type 建议集合

V2.7 建议统一到以下类型集合：

| 类型 | 适用层 | 说明 |
|---|---|---|
| `fact` | 中/长 | 稳定事实 |
| `preference` | 短/中/长 | 用户或团队偏好 |
| `decision` | 中/长 | 设计或项目决策 |
| `constraint` | 短/中/长 | 必须遵守的限制 |
| `risk` | 中/长 | 风险、隐患、注意事项 |
| `task_state` | 短/中 | 正在推进的任务状态 |
| `summary` | 短/中/长 | 摘要型记忆 |
| `issue` | 中/长 | 问题、bug、阻塞 |
| `code_context` | 中/长 | 模块、文件、调用关系、测试策略 |
| `meeting_note` | 中/长 | 会议内容 |
| `hypothesis` | 短/中 | 推测或待验证判断 |
| `procedure` | 中/长 | 操作步骤和流程 |

### 4.2 当前对象到统一类型的映射

| 对象 | 默认类型策略 |
|---|---|
| `AgentContext` | 默认 `task_state` 或 `summary`，视 title/body 判断 |
| `ProjectDocument` | 默认 `code_context`、`meeting_note`、`procedure` 或 `summary` |
| `Memory` | 保留现有 `MemoryKind`，并向统一类型映射 |

## 5. 生命周期状态设计

### 5.1 建议统一状态

| 状态 | 含义 | 是否允许召回 |
|---|---|---|
| `active` | 当前有效 | 是 |
| `candidate` | 已写入但待审查 | 受限 |
| `needs_review` | 有冲突、低置信度或待验证 | 默认否 |
| `archived` | 历史保留但默认不主动召回 | 否 |
| `deprecated` | 已被替代 | 否 |
| `forgotten` | 用户要求遗忘 | 否 |
| `deleted` | 物理删除或逻辑删除完成 | 否 |

### 5.2 当前状态兼容策略

| 当前对象状态 | 统一状态 |
|---|---|
| `MemoryState::Candidate` | `candidate` |
| `MemoryState::Active` | `active` |
| `MemoryState::Archived` | `archived` |
| `MemoryState::Deprecated` | `deprecated` |
| `MemoryState::Conflicted` | `needs_review` |
| `MemoryState::Deleted` | `deleted` |
| `AgentContext` 默认存在态 | `active` |
| `ProjectDocument` 冲突态 | `needs_review` |

## 6. 来源与置信度模型

### 6.1 source_kind

| 来源 | 示例 |
|---|---|
| `conversation` | 用户对话、Agent 执行过程 |
| `file` | 文档、代码文件、README、设计稿 |
| `api` | 外部接口返回 |
| `meeting` | 会议纪要、Minutes |
| `manual` | 用户手工创建 |
| `system` | 系统生成摘要、压缩、治理事件 |
| `legacy` | 老数据回填 |

### 6.2 confidence

| 级别 | 说明 |
|---|---|
| `explicit` | 用户或文档明确陈述 |
| `inferred` | 系统根据多条线索推断 |
| `unverified` | 可能合理但未证实 |
| `stale` | 过去可能成立，现在需要重验 |

V2.7 的原则是：

- 推断绝不伪装成事实
- 低置信度内容可以保留，但必须影响召回和治理

## 7. 统一生命周期服务

V2.7 建议新增以下服务概念：

| 服务 | 职责 |
|---|---|
| `LifecycleNormalizer` | 把三层对象映射成统一 `Memory Record` |
| `RecordClassifier` | 识别 `record_type`、`source_kind`、`confidence` |
| `RecordCompressor` | 生成 `summary` 和多粒度摘要 |
| `RecordUpdater` | 决定新增、跳过、更新、归档或标记 review |
| `RecordResolver` | 处理 supersede、conflict、deprecate、archive |

## 8. 建议的写入流程

```text
raw input / existing object
  -> layer detection
  -> normalize into memory record
  -> classify type/source/confidence
  -> generate summary if needed
  -> dedupe / conflict / supersede check
  -> write or update native object
  -> emit relation and audit event
```

## 9. 迁移策略

### 9.1 迁移目标

V2.7 不要求一次性重迁所有底层表。

更稳妥的路径是：

1. 先引入统一 record 视图和映射逻辑
2. 再逐步把常用字段下沉到存储层
3. 最后再决定是否拆新表

### 9.2 迁移原则

- 旧数据优先兼容读取
- 缺字段时使用保守默认值
- 不做激进自动推断
- 保证 V2.4-V2.6 入口不回退

## 10. V2.7 在 schema 层的关键结果

如果这一层做对了，后续：

- recall 可以按统一字段做过滤和排序
- governance 可以按统一状态做批量治理
- explanation 可以解释每条记录的来源和召回原因
- audit 可以统一记录跨层操作

这也是 V2.7 最核心的底座工作。
