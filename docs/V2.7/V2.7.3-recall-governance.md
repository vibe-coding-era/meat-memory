# V2.7.3 召回、解释、演进与治理设计

状态：Planning Draft

更新时间：2026-04-17

## 1. 设计目标

V2.7 要解决的不是“能不能搜到”，而是：

- 什么时候应该召回
- 应该召回哪一层
- 应该召回多少
- 为什么召回
- 什么内容不应该再被主动召回

## 2. 召回设计

### 2.1 召回流程

```text
current task context
  -> detect task intent
  -> detect scope and layer priorities
  -> retrieve candidates
  -> lifecycle/privacy filtering
  -> rank
  -> budget packing
  -> explanation
  -> context injection
```

### 2.2 召回优先顺序

| 任务类型 | 短期优先 | 中期优先 | 长期优先 |
|---|---|---|---|
| coding | 当前 task 状态、最近工具结果 | 项目文档、模块说明 | 决策、约束、历史问题 |
| review | 当前评审目标和边界 | 测试文档、模块文档 | 历史 bug、评审偏好、发布规则 |
| debug | 最近错误上下文 | runbook、故障文档 | 历史修复经验、约束、风险 |
| planning | 当前目标和待办 | 项目阶段文档 | 目标、原则、历史决策 |
| sync/report | 最近执行摘要 | 项目工作集 | 稳定背景和长期经验 |

### 2.3 召回过滤规则

V2.7 应增加 `RecallGuard`，默认过滤：

- `forgotten`
- `deleted`
- `deprecated`
- `archived`
- `needs_review`
- 过期内容
- 未授权的 `restricted` 内容
- 跨 scope 未授权内容

其中 `needs_review` 可以在用户明确要求时作为“待核实上下文”附带返回，但默认不主动注入。

### 2.4 排序策略

建议先使用可解释的规则权重，而不是黑盒策略：

```text
score =
  task_match * 0.25
  + semantic_similarity * 0.25
  + keyword_match * 0.15
  + scope_match * 0.10
  + layer_priority * 0.10
  + confidence_weight * 0.10
  + freshness_weight * 0.05
```

### 2.5 预算策略

V2.7 应先实现保守预算策略：

- summary first
- high-score item 可带 full content
- 保证层次多样性，避免全是同类记忆
- 限制重复内容
- 对中低置信度内容使用更高进入门槛

## 3. 召回解释设计

### 3.1 为什么必须做 explanation

如果用户无法知道“为什么召回”，系统就很难被信任。

### 3.2 建议的解释字段

| 字段 | 说明 |
|---|---|
| `reason` | 简短召回原因 |
| `matched_scope` | 命中的 scope |
| `matched_layer` | 命中的记忆层 |
| `matched_type` | 命中的统一类型 |
| `matched_terms` | 匹配到的关键词或实体 |
| `status` | 生命周期状态 |
| `confidence` | 置信度 |
| `score` | 最终排序分 |

### 3.3 示例

```json
{
  "record_id": "rec_xxx",
  "reason": "Matched current review task and historical release constraint.",
  "matched_scope": "project:scp_meat_memory_v1",
  "matched_layer": "long_term",
  "matched_type": "constraint",
  "confidence": "explicit",
  "score": 0.87
}
```

## 4. 压缩与摘要设计

### 4.1 V2.7 应先做的摘要类型

| 摘要类型 | 目标 |
|---|---|
| session summary | 压缩当前对话或执行过程 |
| task summary | 保留目标、约束、决策、结果、待办 |
| project summary | 保留当前阶段、重要决策、风险和未完成事项 |

### 4.2 task summary 模板

| 字段 | 说明 |
|---|---|
| `goal` | 任务目标 |
| `constraints` | 用户和工程约束 |
| `decisions` | 形成的决策 |
| `changes` | 完成的动作或变更 |
| `open_questions` | 未解问题 |
| `next_steps` | 下一步 |
| `evidence` | 主要来源 |

### 4.3 V2.7 的压缩原则

- 摘要必须保留约束和原因
- 摘要必须保留待办和未完成项
- 摘要必须可追溯来源
- 摘要优先服务召回，而不是作为纯展示文本

## 5. 演进设计

### 5.1 为什么 V2.7 要补演进

没有演进，系统只会无限追加：

- 旧决策不会退场
- 新事实无法替代旧事实
- 冲突内容会一起召回

### 5.2 建议的关系类型

| 关系 | 作用 |
|---|---|
| `derived_from` | 由上下文、文档、摘要派生 |
| `related_to` | 泛关联 |
| `mentions` | 提到某实体 |
| `depends_on` | 依赖关系 |
| `supersedes` | 新内容替代旧内容 |
| `conflicts_with` | 新旧内容冲突 |

### 5.3 演进策略

| 场景 | 动作 |
|---|---|
| 新决策替代旧决策 | 建立 `supersedes`，旧记录标记 `deprecated` |
| 新事实与旧事实冲突 | 建立 `conflicts_with`，双方或旧记录标记 `needs_review` |
| 新摘要覆盖旧上下文 | 建立 `derived_from` |
| 重复内容写入 | 跳过或合并摘要 |

### 5.4 V2.7 的保守原则

- 不自动硬删除旧记忆
- 冲突先标记，不直接覆盖
- 替代必须可追溯

## 6. 遗忘与治理设计

### 6.1 治理层目标

V2.7 要让系统从“会记”变成“会负责”。

### 6.2 治理动作

| 动作 | 说明 |
|---|---|
| `archive` | 历史保留，不主动召回 |
| `deprecate` | 已被替代 |
| `forget` | 用户要求遗忘，默认 soft forget |
| `delete` | 高风险或强制删除 |
| `restore` | 从 archived / forgotten 恢复 |
| `mark_review` | 标记待核实 |

### 6.3 soft forget 与 hard delete

| 策略 | 说明 |
|---|---|
| `soft_forget` | 改状态为 `forgotten`，从召回中排除，保留审计 |
| `hard_delete` | 物理删除正文或整条记录，保留最小审计元数据 |

V2.7 推荐先做 `soft_forget`，再做高风险 `hard_delete`。

### 6.4 隐私与敏感规则

默认高风险内容：

- API key / token / secret
- 凭证文件正文
- 私密路径
- 未经确认的个人敏感信息

默认策略：

- 不主动长期保存
- 不主动召回
- 尽量脱敏后保留必要上下文

## 8. V2.7 的治理闭环

V2.7 完成后，治理链路应变成：

```text
record created
  -> classified
  -> summarized
  -> recalled or skipped
  -> stale/conflict/supersede detected
  -> archived/deprecated/needs_review/forgotten
  -> audited
```

## 9. 本阶段优先级建议

召回与治理部分建议按以下顺序推进：

1. `RecallGuard`
2. `RecallExplanation`
3. `TaskSummary`
4. `Supersede / Conflict Marking`
5. `Soft Forget`
6. `Audit Log`
7. `Governance Report`

这个顺序能最小成本地提升用户体验，同时为后续更复杂能力立住边界。
