# V2.8.1 同项目识别、同内容判定与 Merge 策略

状态：Implemented Design

更新时间：2026-04-24

## 1. 设计目标

V2.8 需要先解决两个经常被混在一起的问题：

1. 当前输入是不是属于同一个项目
2. 当前输入和已有记忆是不是同一个内容

这两个问题必须拆开判断，否则系统会出现两个极端：

- 跨项目误合并
- 同项目内无限追加

## 2. 问题拆解

### 2.1 “同一项目”不等于“同一内容”

例子：

- 同一个项目里，两个不同决策不能合并
- 不同项目里，相同标题的 “发布流程” 不能默认合并

### 2.2 “同一内容”也不等于“应该覆盖”

例子：

- 新决策替代旧决策：应走 `supersede`
- 新事实与旧事实矛盾：应走 `conflict`
- 同一事实的新证据补充：可走 `new_version`

## 3. 同项目识别模型

V2.8 建议把项目识别拆成三类信号：

| 信号层 | 示例 | 可信度 | 是否可自动使用 |
|---|---|---|---|
| 强信号 | `scope_id` 明确命中、已确认的 repo root 绑定、source_id 命中 | 高 | 是 |
| 中信号 | `source_ref`、canonical path、git remote、project alias、owner scope | 中 | 仅作建议 |
| 弱信号 | 标题、目录名、模块实体、历史相邻访问记录 | 低 | 否 |

### 3.1 强信号优先级

建议优先级：

1. 显式传入的 `scope_id`
2. 用户已确认的项目绑定
3. `MemorySource.local_root` / canonical root
4. 已知 repo remote / repo id

### 3.2 用户确认的项目绑定

V2.8 建议新增 `ProjectIdentityBinding`，用于记住用户确认结果。

建议字段：

| 字段 | 说明 |
|---|---|
| `binding_id` | 绑定 id |
| `owner_scope_id` | 归属 scope |
| `binding_kind` | `repo_root` / `remote_url` / `source_ref_prefix` / `alias` |
| `binding_value` | 绑定值 |
| `canonical_project_key` | 规范化项目键 |
| `confirmed_by` | `user` / `system` |
| `confidence` | 绑定置信度 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

### 3.3 何时询问用户

| 场景 | 策略 |
|---|---|
| 明确命中已有强绑定 | 不问 |
| 新 repo root 首次出现，但路径和 remote 稳定 | 建议问一次 |
| 同名项目存在多个可能 scope | 必须问 |
| 只有标题或主题相似 | 不自动归属，必须问 |

## 4. 同内容判定模型

V2.8 建议不要把判定结果简化成 “merge / no merge”，而是分成五类：

| 类型 | 含义 | 默认动作 |
|---|---|---|
| `exact_duplicate` | 内容与证据几乎一致 | 自动跳过或补证据 |
| `near_duplicate` | 表述不同但核心信息接近 | 生成 merge proposal |
| `supersede_candidate` | 新内容可能替代旧内容 | 生成 supersede proposal |
| `conflict_candidate` | 新旧内容可能矛盾 | 标记 review proposal |
| `unrelated` | 无直接关系 | 新建记录 |

## 5. 关系判定信号

| 信号 | 说明 | 适用场景 |
|---|---|---|
| 规范化 title/body hash | 精确重复 | `exact_duplicate` |
| source/evidence 重合 | 同证据重复写入 | `exact_duplicate` / `near_duplicate` |
| memory kind 一致 | 决策对决策、事实对事实 | `near_duplicate` / `supersede` / `conflict` |
| 实体重叠 | 同文件、同模块、同任务 | `near_duplicate` / `supersede` / `conflict` |
| 时间顺序 | 新旧版本先后 | `supersede` |
| 语义极性差异 | “采用 A” vs “改用 B” | `supersede` / `conflict` |
| 生命周期状态 | 已 deprecated / archived | 帮助裁决 |

## 6. 判定流程

```text
incoming artifact / memory candidate
  -> resolve project identity
  -> retrieve same-scope candidate memories
  -> compare title/body/source/evidence/entities
  -> classify relationship
  -> policy check
  -> auto apply or create proposal
```

## 7. 自动处理与人工确认矩阵

| 场景 | 默认动作 | 是否需要用户 |
|---|---|---|
| 同 scope + 同 evidence + 同规范化内容 | 自动去重 | 否 |
| 同 scope + 近重复 + 非决策类 | merge proposal | 建议确认 |
| 同 scope + 新决策替代旧决策 | supersede proposal | 必须确认 |
| 同 scope + 新旧事实矛盾 | conflict proposal | 必须确认 |
| 跨 scope + 高相似 | cross-project proposal | 必须确认 |
| 用户显式指定 “这是同一条” | 直接进入 proposal apply | 用户已确认 |

## 8. Merge 的保守边界

V2.8 推荐只允许以下场景直接合并：

- `summary` 对 `summary` 的重提炼
- `task_state` 的同任务持续更新
- 同一 `source_ref` 下重复抽取的过程性信息

以下场景默认不直接 merge：

- `decision`
- `fact`
- `constraint`
- `risk`
- `preference`

这些高价值类型应优先走 `new version`、`supersede` 或 `conflict`。

## 9. 判定结果对象

建议新增内核级对象 `RelationshipAssessment`：

```json
{
  "project_key": "proj_meat_memory",
  "matched_scope_id": "scp_meat_memory_v1",
  "relationship": "supersede_candidate",
  "confidence": 0.86,
  "review_level": "required",
  "matched_memory_ids": ["mem_old_decision"],
  "evidence": [
    "same entity: crates/memory-kernel/src/lib.rs",
    "new text contains 改用 / replace",
    "same record_type: decision"
  ]
}
```

## 10. 边界场景

### 10.1 同名不同项目

不能因为都叫 “README cleanup” 就归为同一项目，必须看 scope、repo root、source。

### 10.2 摘要覆盖事实

摘要不能直接替代事实型记忆，只能 `derived_from`。

### 10.3 用户手动纠偏

用户一旦明确指定：

- “这是新项目”
- “这是旧项目的继续”
- “这两条不要合并”

系统应把该判断作为强绑定或强排除规则保存。

### 10.4 跨项目复用经验

跨项目的相似经验应更适合建立 `related_to` 或新的长期经验记忆，而不是直接 merge 到原项目记忆。

## 11. 验收标准

- 同一个 repo 第二次进入时，系统能直接命中已确认项目绑定
- 明确重复写入不会产生多条 active 记忆
- 新决策不会静默覆盖旧决策
- 冲突事实会进入 review，而不是默认被召回
- 用户手工指定的项目边界能够被后续请求复用
