# V2.8.3 版本、时间线、恢复与关系模型

状态：Implemented Design

更新时间：2026-04-24

## 1. 设计目标

V2.8 需要把“记忆变更”从不可追溯的状态改动，升级为可查看时间线、可比较差异、可恢复的版本系统。

但 V2.8 不追求完整分支式版本控制。

推荐目标是：

- 有 snapshot
- 有 semantic relation
- 有 lifecycle audit
- 能 rollback / restore

## 2. 版本模型分层

V2.8 建议保留三条并行轨道：

| 轨道 | 作用 |
|---|---|
| `memory_versions` | 内容快照 |
| `memory_relations` | 新旧记忆之间的语义关系 |
| `memory_lifecycle_audit_events` | 状态变化审计 |

这样可以回答三类问题：

- 这条记忆正文怎么变过
- 它和哪些旧记忆有替代或冲突关系
- 谁在什么时候做了什么治理动作

## 3. 复用现有基础

仓库当前已经有：

- `memory_versions`
- `memory_lifecycle_audit_events`

V2.8 推荐：

- 继续复用 `memory_versions` 作为 snapshot 主表
- 不新建过重的 event store
- 只补充关系表和少量版本元数据

## 4. Snapshot 语义

### 4.1 何时生成新版本

建议以下场景写新 snapshot：

- 标题变更
- 正文变更
- 摘要重写且影响 recall 内容
- evidence 汇总显著变化
- 用户手工修订重要字段

以下场景不必强制写新 snapshot：

- 单纯状态变更
- 单纯 relation 变化
- 单纯审计补记

### 4.2 版本元数据

建议给 `memory_versions` 补以下列：

| 字段 | 说明 |
|---|---|
| `change_kind` | `create` / `edit` / `merge` / `distill` / `rollback` |
| `actor` | `user` / `agent` / `system` |
| `reason` | 变更原因 |
| `source_proposal_id` | 来自哪个 proposal |

## 5. 语义关系模型

建议新增 `memory_relations`：

| relation_type | 含义 |
|---|---|
| `supersedes` | 新记忆替代旧记忆 |
| `conflicts_with` | 新旧记忆冲突 |
| `derived_from` | 摘要 / 提炼来源于原记录 |
| `merged_into` | 原记录合并进目标记录 |
| `related_to` | 泛相关 |

### 5.1 为什么需要 relation 而不只靠版本

因为以下情况不是“同一记忆的新版”：

- 新决策替代旧决策
- 项目总结从多条 task_state 提炼出来
- 两条独立事实彼此冲突

这些都更适合通过关系表达。

## 6. 时间线模型

建议提供 `MemoryTimeline` 查询结果：

```json
{
  "memory_id": "mem_123",
  "current_status": "active",
  "versions": [],
  "relations": [],
  "lifecycle_events": [],
  "proposals": []
}
```

时间线按时间统一展示以下节点：

- create
- version created
- proposal opened
- proposal approved / rejected
- supersede relation created
- conflict marked
- archived / forgotten / restored
- rollback applied

## 7. 恢复模型

### 7.1 `restore`

适用于 lifecycle 状态恢复：

- `forgotten -> active`
- `archived -> active`

### 7.2 `rollback`

适用于内容恢复：

- 当前正文回滚到旧版本 snapshot
- 同时生成一个新的 rollback snapshot，而不是直接覆盖历史

### 7.3 `reopen_review`

适用于治理状态恢复：

- 已 reject 的 proposal 重新打开
- 已 `needs_review` 的冲突重新进入处理队列

## 8. 状态与版本的交互原则

| 动作 | 是否新版本 | 是否 relation | 是否 audit |
|---|---|---|---|
| 编辑正文 | 是 | 否 | 是 |
| supersede | 否或可选 | 是 | 是 |
| conflict_mark | 否 | 是 | 是 |
| archive | 否 | 否 | 是 |
| forget | 否 | 否 | 是 |
| rollback | 是 | 可选 | 是 |

推荐原则：

- 内容变化优先写 snapshot
- 语义变化优先写 relation
- 治理动作始终写 audit

## 9. Hard Delete 边界

V2.8 仍建议将 `hard_delete` 视为受限操作。

推荐策略：

- 物理删除正文或记录
- 只保留最小审计元数据
- 如果来自敏感信息策略，必须记录删除原因

对 `hard_delete` 不建议提供普通 rollback，只能保留：

- 删除动作审计
- 原因
- 发起人

## 10. Recall 与时间线的关系

默认 recall 仍应遵循 V2.7 guard：

- `needs_review`
- `deprecated`
- `archived`
- `forgotten`

不会主动进入 recall。

但 timeline 查询必须能看见这些历史状态，否则用户无法理解为什么一条记忆“消失了”。

## 11. Markdown Projection 策略

V2.8 不建议把完整版本时间线都投影到 Markdown。

推荐做法：

- Markdown 继续承载当前有效 memory 表达
- 版本、proposal、审计、timeline 以 PG 为准
- 若需要导出人类可读报告，再单独生成 timeline/export 文档

这样可以避免 projection 变成难维护的历史账本。

## 12. 验收标准

- 每次正文变更都可在版本列表中看到 snapshot
- `supersede` 和 `conflict` 可在时间线中追溯
- `rollback` 会生成新的 rollback 版本而不是抹掉历史
- `restore` 能恢复 forgotten / archived 记忆
- recall 不会把 deprecated / needs_review 内容静默注入，但 timeline 仍能完整展示
