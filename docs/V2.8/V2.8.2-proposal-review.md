# V2.8.2 Proposal、Review Queue 与用户确认流程

状态：Implemented Design

更新时间：2026-04-24

## 1. 设计目标

V2.8 的治理核心不是“系统自动改”，而是“系统能给出可解释提案，并让用户在关键点做判断”。

因此 V2.8 需要一个独立的 `MemoryProposal` 层。

## 2. 为什么需要 Proposal 层

没有 proposal 层时，系统只能二选一：

- 要么静默自动更新，风险高
- 要么什么都不做，记忆越积越乱

proposal 层的价值是把动作拆成两步：

1. 先提出 “建议怎么改”
2. 再决定 “要不要执行”

## 3. Proposal 类型

建议支持以下 `proposal_type`：

| 类型 | 说明 |
|---|---|
| `merge` | 建议把近重复内容合并为一条或一版 |
| `new_version` | 建议为已有记忆生成新版本 |
| `supersede` | 建议新内容替代旧内容 |
| `conflict_mark` | 建议把相关记录标记为 `needs_review` |
| `archive` | 建议归档低活跃或过期记忆 |
| `forget` | 建议 soft forget |
| `restore` | 建议恢复已 forgotten / archived 记忆 |
| `hard_delete` | 建议物理删除高敏感内容 |
| `distill_upsert` | 建议按 profile 生成或更新提炼记忆 |

## 4. Review Level

建议每个 proposal 都带 `review_level`：

| 级别 | 含义 | 示例 |
|---|---|---|
| `auto` | 可自动执行，只保留审计 | 精确重复去重 |
| `suggested` | 可先展示，允许批量批准 | 非高风险 near duplicate |
| `required` | 必须用户明确批准 | supersede / conflict / cross-project merge |
| `blocked` | 在额外信息补齐前不能执行 | 项目归属不明确、目标记忆不唯一 |

## 5. Proposal 数据结构

建议字段：

| 字段 | 说明 |
|---|---|
| `proposal_id` | 提案 id |
| `scope_id` | 归属 scope |
| `proposal_type` | 提案类型 |
| `status` | `open` / `approved` / `rejected` / `applied` / `canceled` / `expired` |
| `review_level` | 审核级别 |
| `subject_memory_id` | 当前输入或主记忆 |
| `target_memory_ids` | 候选目标记忆 |
| `reason` | 生成原因 |
| `evidence` | 证据列表 |
| `patch_summary` | 预计变更摘要 |
| `confidence` | 提案置信度 |
| `created_by` | `system` / `agent` / `user` |
| `decided_by` | 决策者 |
| `decided_at` | 决策时间 |
| `applied_at` | 执行时间 |
| `expires_at` | 过期时间 |

## 6. 状态流转

```text
open
  -> approved
  -> rejected
  -> canceled
  -> expired

approved
  -> applied
  -> canceled
```

建议原则：

- `approved` 不等于已经生效
- `applied` 必须对应实际执行成功
- 所有转移都要写 audit

## 7. 典型流程

### 7.1 写入时发现近重复

```text
remember request
  -> relationship classifier says near_duplicate
  -> create merge proposal
  -> return proposal summary
  -> user approve
  -> executor creates new version or merges summary
```

### 7.2 写入时发现新决策替代旧决策

```text
remember request
  -> detect supersede candidate
  -> create supersede proposal
  -> user approve
  -> new memory active
  -> old memory deprecated
  -> relation created
```

### 7.3 维护任务发现 stale memory

```text
maintenance job
  -> detect stale / long-unused memories
  -> create archive proposal batch
  -> user review
  -> apply approved items
```

## 8. 用户交互要求

### 8.1 用户必须看到的内容

每条 proposal 至少展示：

- 建议动作是什么
- 影响哪些记忆
- 为什么做出这个判断
- 执行后状态会怎么变化
- 是否可恢复，如何恢复

### 8.2 用户可做的动作

- `approve`
- `reject`
- `approve with edit`
- `snooze`
- `show diff`
- `show evidence`
- `apply in batch`

V2.8 MVP 可先做：

- `approve`
- `reject`
- `show evidence`
- `show diff`

## 9. Review Queue 视图

建议支持以下维度筛选：

- `status`
- `proposal_type`
- `review_level`
- `scope_id`
- `memory_kind`
- `created_by`
- `created_at` / `expires_at`

推荐排序：

1. `required`
2. `blocked`
3. 高置信度 `suggested`
4. 低风险 `auto` 审计项

## 10. 接入面设计

### 10.1 CLI

已实现：

- `memory-cli proposals list`
- `memory-cli proposals inspect <proposal_id>`
- `memory-cli proposals approve <proposal_id>`
- `memory-cli proposals reject <proposal_id>`
- `memory-cli proposals apply <proposal_id>`

### 10.2 HTTP

已实现：

- `GET /api/v1/proposals`
- `GET /api/v1/proposals/{proposal_id}`
- `POST /api/v1/proposals/{proposal_id}/approve`
- `POST /api/v1/proposals/{proposal_id}/reject`
- `POST /api/v1/proposals/{proposal_id}/apply`
- `POST /api/v1/proposals/review-policy/evaluate`

### 10.3 MCP

已实现：

- `memory.proposals.list`
- `memory.proposals.inspect`
- `memory.proposals.approve`
- `memory.proposals.reject`
- `memory.proposals.apply`

MCP 的原则应是：

- Agent 可以提出 proposal
- Agent 不应默认批准 `required` proposal，除非用户显式授权

## 11. 审计与权限

| 动作 | 默认 actor |
|---|---|
| 生成 proposal | `system` / `agent` |
| 批准高风险 proposal | `user` |
| 执行 approved proposal | `system` |
| 回滚 | `user` / 受控 `agent` |

高风险动作需要记录：

- 原因
- 批准人
- 执行结果
- 对应 version / relation / lifecycle audit id

## 12. 非目标

V2.8 不需要一开始提供复杂 GUI 审批中心。

MVP 只要保证：

- CLI 可查可批
- HTTP 可查可批
- MCP 可受控访问

就已经能支撑主链路。

## 13. 验收标准

- 系统发现 near duplicate 时会创建 proposal，而不是静默 merge
- `supersede` / `conflict_mark` 提案默认进入 `required`
- proposal 的 `approve`、`reject`、`apply` 都有审计
- 用户能看到 evidence、patch summary、预计状态变化
- MCP 不会绕过 review level 直接执行高风险 proposal
