# V2.8.4 用户可配置的记忆提炼模型

状态：Implemented Design

更新时间：2026-04-24

## 1. 设计目标

V2.8 需要把“系统认为值得记住什么”从纯系统黑盒规则，升级为“系统基线 + 用户偏好 + 项目偏好”的可配置提炼流程。

但这个配置必须有边界：

- 用户可以影响提炼重点
- 用户不能让系统伪造来源或篡改事实

## 2. Distillation Profile 的定位

`Distillation Profile` 不是直接存 prompt 文本这么简单。

它应该是：

- 一套可组合的提炼偏好
- 一套输出约束
- 一套候选记忆筛选规则

## 3. Profile 分层

建议分成四层：

| 层级 | 作用 | 是否持久化 |
|---|---|---|
| `system_base` | 不可绕过的基线规则 | 是，内置 |
| `user_global` | 用户跨项目偏好 | 是 |
| `project` | 某个 scope / project 的记忆偏好 | 是 |
| `session_override` | 当前会话临时偏好 | 否或短期 |

### 3.1 组合顺序

```text
system_base
  -> user_global
  -> project
  -> session_override
```

后层可以补充或缩小前层，但不能覆盖基础安全规则。

## 4. 用户可配置什么

建议开放以下配置项：

| 配置项 | 说明 |
|---|---|
| `focus_topics` | 更希望沉淀哪些主题 |
| `prefer_memory_kinds` | 更偏好提炼成哪些记忆类型 |
| `ignore_patterns` | 哪些内容默认不记 |
| `summary_style` | 摘要风格，如偏简洁或偏结构化 |
| `promotion_threshold` | 什么样的内容值得从 task/state 升级为长期记忆 |
| `evidence_requirements` | 至少需要多少来源或证据 |
| `language_preference` | 中文、英文或双语输出 |

## 5. 不可被用户覆盖的基线

以下规则建议写进 `system_base`：

- 必须保留来源和 evidence
- 必须标记 `confidence`
- 不得把推断伪装成事实
- 不得让 prompt 直接绕过 scope / sensitivity / recall guard
- 冲突和 supersede 仍需要关系与提案，不得仅靠 prompt 决定

## 6. 输出合同

提炼结果建议先生成 `distillation candidates`，而不是直接写 memory。

建议输出结构：

```json
{
  "candidates": [
    {
      "title": "Memory merge should be proposal-first",
      "memory_kind": "decision",
      "body": "V2.8 should require user approval for supersede/conflict actions.",
      "confidence": "explicit",
      "why_keep": "cross-session design rule",
      "evidence_refs": ["agent-context://ctx_1"]
    }
  ],
  "discarded": [],
  "warnings": []
}
```

## 7. Preview-first 流程

V2.8 推荐提炼流程：

```text
raw context / task summary / document
  -> compose profile
  -> generate distillation candidates
  -> preview
  -> user edit or approve
  -> write proposal or apply
```

这意味着：

- 用户可以先看候选
- 用户可以改 profile 再重跑
- 系统不会因为一次 prompt 写错就直接污染长期记忆

## 8. Distill 与 Proposal 的关系

提炼结果进入系统后，建议仍走 proposal 层。

| 场景 | 建议动作 |
|---|---|
| 全新知识 | `distill_upsert` proposal 或低风险直接写 candidate |
| 命中近重复 | 生成 `merge` proposal |
| 命中旧决策 | 生成 `supersede` proposal |
| 命中矛盾事实 | 生成 `conflict_mark` proposal |

## 9. 数据模型建议

建议新增 `distillation_profiles`：

| 字段 | 说明 |
|---|---|
| `profile_id` | profile id |
| `scope_id` | 所属 scope，可空表示用户全局 |
| `profile_level` | `user_global` / `project` |
| `name` | 名称 |
| `status` | `active` / `archived` |
| `prompt_text` | 用户提示词正文 |
| `rules_json` | 结构化规则 |
| `created_by` | 创建人 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

建议新增 `distillation_runs`：

| 字段 | 说明 |
|---|---|
| `run_id` | 运行 id |
| `profile_id` | 使用的 profile |
| `scope_id` | 运行 scope |
| `source_ref` | 来源 |
| `preview` | 是否 preview |
| `input_hash` | 输入摘要哈希 |
| `output_json` | 候选结果 |
| `created_at` | 运行时间 |

## 10. CLI / HTTP / MCP 入口

### 10.1 CLI

- `memory-cli profiles list`
- `memory-cli profiles upsert`
- `memory-cli profiles archive`
- `memory-cli distill preview`

### 10.2 HTTP

- `GET /api/v1/distillation/profiles`
- `PUT /api/v1/distillation/profiles/{profile_id}`
- `POST /api/v1/distillation/preview`

### 10.3 MCP

- `memory.profile.list`
- `memory.profile.upsert`
- `memory.distill.preview`

V2.8 保持 `preview-first` 边界，不提供直接 `distill apply` 入口；候选写入应继续走 proposal/review 治理链路。

## 11. 反模式

V2.8 应避免以下设计：

- 只保存一段自由 prompt，没有结构化规则
- 用户 prompt 直接覆盖 `confidence` / `source_kind`
- 提炼结果不经 preview 直接进入长期 active memory
- 用 prompt 代替 supersede/conflict 决策逻辑

## 12. 验收标准

- 用户可以配置全局和项目级 distillation profile
- preview 结果包含候选记忆、证据和保留原因
- 同一输入可在更换 profile 后重跑
- profile 不会绕过基础来源、置信度和治理规则
- distill 输出命中近重复 / 冲突时仍会进入 proposal 流程
