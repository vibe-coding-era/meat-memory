# V2.8.5 技术架构、存储与接口设计

状态：Implemented Design

更新时间：2026-04-24

## 1. 架构定位

V2.8 不是新开一套 memory engine，而是在现有 `memory-domain`、`memory-kernel`、`memory-store-pg`、`memory-http`、`memory-mcp`、`memory-cli` 之上增加一层治理编排。

推荐分层：

| 层 | 模块 | 职责 |
|---|---|---|
| Domain | 新增 proposal/profile/relation/project identity 对象 | 建模 |
| Kernel | resolver/classifier/orchestrator/executor/version manager | 编排 |
| Store | proposal/relation/profile/project binding 持久化 | 存储 |
| API | HTTP / CLI / MCP 新入口 | 接入 |
| Policy | review level / approval / rollback / prompt guard | 策略 |

## 2. 核心服务

### 2.1 `ProjectIdentityResolver`

职责：

- 基于 `scope_id`、binding、source、repo root 判断项目归属
- 在不确定时返回多候选结果

### 2.2 `RelationshipClassifier`

职责：

- 对输入和候选 memory 做 duplicate / supersede / conflict 分类
- 输出 `RelationshipAssessment`

### 2.3 `ProposalOrchestrator`

职责：

- 根据 assessment 和 policy 生成 `MemoryProposal`
- 决定 `review_level`
- 对 `auto` proposal 直接转交 executor

### 2.4 `ProposalExecutor`

职责：

- 执行 approved proposal
- 写 snapshot / relation / lifecycle audit

### 2.5 `VersionManager`

职责：

- 创建新版本
- 管理 rollback
- 暴露 version diff 和 version list

### 2.6 `TimelineQueryService`

职责：

- 聚合 versions、relations、audit、proposals
- 返回统一 timeline payload

### 2.7 `DistillationProfileService`

职责：

- 组合 system/user/project/session profile
- 提供 CRUD 和 active profile 解析

### 2.8 `DistillationPreviewService`

职责：

- 基于 profile 生成候选记忆
- 不直接落库
- 与 proposal 系统联动

## 5. 为什么不做通用 Fingerprint 表

V2.8 不建议一开始引入通用 `memory_fingerprints` 表。

原因：

- 当前已有 search、source_refs、entity extraction、memory kind 可用于候选召回
- dedupe / supersede / conflict 的判定更像 kernel 规则，而不是单表主导
- 太早持久化 fingerprint，容易把还不稳定的策略固化到 schema

因此建议：

- 候选检索依赖现有 store
- 规范化 hash 只在比较期计算
- 最终只持久化 proposal evidence 和决策结果

## 7. 执行链路

### 7.1 Write-time governance

```text
remember request
  -> ProjectIdentityResolver
  -> RelationshipClassifier
  -> ProposalOrchestrator
  -> if auto: ProposalExecutor
  -> else: persist proposal and return review item
```

### 7.2 Proposal apply

```text
approve proposal
  -> ProposalExecutor
  -> write version / relation / lifecycle audit
  -> update proposal status
```

### 7.3 Distillation preview

```text
raw context
  -> compose profile
  -> generate candidates
  -> classify candidates against existing memories
  -> return preview + downstream proposal suggestions
```

## 8. PG 与 Markdown 的职责分工

建议 V2.8 保持以下边界：

| 能力 | PG | Markdown |
|---|---|---|
| current memory state | 主存 | projection |
| proposal queue | 主存 | 不投影 |
| version timeline | 主存 | 不投影 |
| relation graph | 主存 | 可选摘要投影 |
| distillation profiles | 主存 | 不投影 |

理由：

- proposal / timeline / relation 更像系统控制面数据
- Markdown 更适合作为当前有效知识 projection，而不是完整审计账本

## 9. 向后兼容策略

### 9.1 与 V2.7 兼容

- 现有 `remember/search/fetch_context/forget/restore` 入口保持可用
- 新 proposal 流程只在 V2.8 开启时介入高风险关系判定
- recall guard 继续复用 V2.7 规则

### 9.2 与 Markdown-only 兼容

建议声明：

- V2.8 完整 proposal/timeline/profile 功能以 PG 为主
- Markdown-only 模式可继续基本 remember/search
- 没有 PG 时，review queue 和 timeline 降级为不可用或只读最小输出

## 11. 迁移策略

推荐顺序：

1. 新建 proposal / relation / profile / binding 表
2. 扩充 `memory_versions`
3. 在 kernel 中接入 resolver / classifier / orchestrator
4. 接入 HTTP / CLI / MCP
5. 最后接入 distillation preview/apply

## 12. 验收标准

- 提案、关系、profile、binding 都有明确持久化模型
- `memory_versions` 足以解释版本变更来源
- timeline 查询能聚合 versions、relations、proposal、audit
- PG / Markdown 边界清晰，不会把 projection 变成复杂审计账本
- 现有 V2.7 recall/forget/restore 主链路不被破坏
