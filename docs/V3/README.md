# Meat Memory V3 总方案

状态：Planning Draft

更新时间：2026-04-13

## 1. 版本定位

Meat Memory V3 的目标是把系统从“可写入、可检索的记忆库”升级为“能理解、压缩、关联、遗忘、演进的项目认知系统”。

V3 不只解决存储问题，而是围绕 Agent 的持续协作能力建立完整记忆生命周期：

- 短期记忆负责当前任务不断线
- 中期记忆负责项目过程不断片
- 长期记忆负责稳定知识不白费
- 理解、压缩、关联、遗忘、演进让三层记忆从存储变成协作能力

## 2. 总目标

| 目标 | 说明 |
|---|---|
| 从存储走向理解 | 记忆不只是文本，而是带类型、来源、置信度、作用域、生命周期的知识单元 |
| 从检索走向召回 | 系统能判断何时需要记忆、该召回哪些、如何控制数量 |
| 从追加走向演进 | 新事实出现时能更新旧记忆，而不是无限追加 |
| 从保留走向治理 | 支持遗忘、降权、归档、冲突处理、敏感信息控制 |
| 从孤立走向关联 | 建立任务、决策、代码、会议、偏好、问题之间的关系网 |

## 3. 用户故事

| 角色 | 用户故事 | 价值 |
|---|---|---|
| 开发者 | 作为开发者，我希望 Agent 能自动拉取当前项目相关历史上下文，这样我不用每次重复解释背景 | 降低重复沟通成本 |
| 项目维护者 | 作为维护者，我希望项目决策、架构变化、踩坑记录能长期沉淀并更新 | 保持项目认知连续 |
| Agent | 作为 Agent，我希望能区分事实、推测、偏好、计划、临时状态 | 避免把错误信息当事实使用 |
| 用户 | 作为用户，我希望能查看、修改、删除或要求遗忘某些记忆 | 增强可控性和信任 |
| 团队成员 | 作为团队成员，我希望记忆能关联代码、需求、会议、任务和决策 | 提升协作与追溯效率 |
| 安全负责人 | 作为安全负责人，我希望敏感信息不会被随意长期保存或主动召回 | 降低隐私与合规风险 |

## 4. 核心场景

| 场景 | 目标行为 |
|---|---|
| 新会话接续项目 | 自动识别项目 scope，召回项目背景、当前阶段、关键约束 |
| 开始代码任务 | 召回相关模块、历史 bug、测试方法、设计决策 |
| 任务结束 | 生成任务摘要，提取值得沉淀的知识，归档临时上下文 |
| 发现新事实 | 检查是否与旧记忆冲突，更新或标记旧记忆 |
| 记忆过期 | 自动降权、标记待验证，必要时归档 |
| 用户要求遗忘 | 删除或屏蔽指定记忆，并记录治理操作 |
| 长上下文压缩 | 保留意图、决策、约束、未完成事项和来源 |
| 项目复盘 | 按时间线、主题、模块聚合历史记忆与演进记录 |

## 5. 功能分解

| 模块 | 功能 | 说明 |
|---|---|---|
| 记忆模型 | 类型、作用域、来源、置信度、生命周期 | 建立统一 Memory Schema |
| 理解引擎 | 信息抽取、分类、重要性判断 | 判断什么值得记、属于哪类记忆 |
| 压缩引擎 | 多粒度摘要、去重、保真压缩 | 对对话、任务、会议、文档做摘要 |
| 召回引擎 | 检索、排序、上下文预算控制 | 在合适时机召回合适内容 |
| 关联引擎 | 实体关系、主题关系、代码关系 | 建立轻量知识图谱 |
| 演进引擎 | 冲突检测、版本化、记忆更新 | 管理记忆从旧状态到新状态的变化 |
| 遗忘治理 | 删除、归档、降权、敏感信息处理 | 控制记忆生命周期 |
| 用户控制台 | 查看、编辑、删除、审计 | 提供可控与可解释能力 |
| 评估体系 | 召回准确率、噪音率、冲突率 | 衡量 V3 能力是否有效 |

## 6. 技术总架构

| 层 | 模块 | 职责 |
|---|---|---|
| 接入层 | API / CLI / MCP Tools | 提供记忆写入、检索、更新、删除、治理、报告能力 |
| 编排层 | Memory Orchestrator | 决定何时理解、压缩、召回、更新、遗忘 |
| 智能层 | Understanding / Compression / Recall / Evolution Engine | 负责分类、摘要、排序、冲突检测、演进判断 |
| 存储层 | Memory Store / Relation Store / Audit Log | 保存记忆、关系、版本、审计事件 |
| 策略层 | Scope Policy / Lifecycle Policy / Privacy Policy / Budget Policy | 管理作用域、生命周期、敏感信息、上下文预算 |
| 评估层 | Evaluation Harness | 评估召回质量、摘要保真、冲突检测、噪音率 |

## 7. 整体流程

### 7.1 写入流程

```text
raw input
  -> scope detection
  -> understanding
  -> compression
  -> dedupe/conflict check
  -> memory upsert
  -> relation update
  -> audit event
```

### 7.2 召回流程

```text
current task context
  -> intent/scope detection
  -> candidate retrieval
  -> ranking
  -> lifecycle/privacy filtering
  -> token budget packing
  -> explanation
  -> context injection
```

### 7.3 维护流程

```text
scheduled/manual trigger
  -> stale detection
  -> conflict review
  -> archive/deprecate/forget
  -> health report
```

## 9. 建议验收指标

| 指标 | 目标 |
|---|---|
| 召回准确率 | 当前任务召回的记忆中，大部分与任务直接相关 |
| 召回噪音率 | 无关记忆进入上下文的比例持续下降 |
| 摘要保真率 | 摘要保留目标、约束、决策、原因、待办 |
| 冲突发现率 | 新旧事实矛盾时能被标记 |
| 过期记忆占比 | 长期 active 记忆中明显过期内容下降 |
| 用户可控性 | 用户能查看、修改、删除、解释主要记忆 |
| 安全性 | 敏感信息默认不被长期保存或主动召回 |

## 11. 推进原则

V3.1 必须优先落地。V3 最大的工程风险不是某个分类器不够聪明，而是底层数据没有把类型、来源、状态、生命周期、关系立住。只要这层稳定，后续理解、召回、演进和治理都能逐步替换策略，不需要推倒重来。
