# Meat Memory V3.3 召回与上下文预算

状态：Planning Draft

更新时间：2026-04-13

## 1. 版本目标

V3.3 让记忆真正进入 Agent 工作流：系统能判断何时需要召回、召回哪些内容、召回多少内容，以及为什么召回这些内容。

一句话目标：让记忆少而准地进入上下文。

## 2. 产品方案

### 2.1 用户故事

| 角色 | 用户故事 | 价值 |
|---|---|---|
| 开发者 | 我希望开始 coding/debug/review 时自动带入相关项目背景 | 减少重复解释 |
| Agent | 我希望根据当前任务和 token 预算选择最有用的记忆 | 提高任务执行质量 |
| 用户 | 我希望知道系统为什么召回某几条记忆 | 增强透明度 |
| 项目维护者 | 我希望过期、低置信度、敏感或跨 scope 的记忆不会乱入上下文 | 降低误召回风险 |

### 2.2 核心场景

| 场景 | 行为 |
|---|---|
| 代码任务 | 优先召回 code_context、decision、issue、task_state |
| Review 任务 | 优先召回历史 bug、设计约束、测试策略 |
| Debug 任务 | 优先召回相关模块、错误记录、历史修复经验 |
| 规划任务 | 优先召回项目目标、版本方案、未完成事项 |
| 长上下文限制 | 只注入 summary，必要时附少量 full content |

### 2.3 功能分解

| 功能 | 说明 | 优先级 |
|---|---|---|
| 召回意图识别 | 判断当前任务是否需要召回记忆 | P0 |
| 候选记忆检索 | 按 scope、关键词、语义相关性检索 | P0 |
| 召回排序 | 综合相关性、时效性、置信度、作用域 | P0 |
| 上下文预算控制 | 控制注入 token 数，避免噪音 | P1 |
| 召回解释 | 返回为什么召回这些记忆 | P1 |
| 任务型召回模板 | coding、review、debug、planning、meeting | P1 |
| 负召回策略 | 明确哪些记忆不应进入当前上下文 | P2 |

## 3. 技术方案

### 3.1 召回流程

```text
current task context
  -> recall intent detection
  -> scope detection
  -> candidate retrieval
  -> ranking
  -> lifecycle/privacy filtering
  -> token budget packing
  -> explanation
  -> context injection
```

### 3.2 服务模块

| 模块 | 职责 |
|---|---|
| `RecallEngine` | 编排召回全流程 |
| `RecallIntentDetector` | 判断任务类型和召回必要性 |
| `CandidateRetriever` | 混合检索候选记忆 |
| `MemoryRanker` | 排序候选记忆 |
| `RecallGuard` | 过滤 forgotten、敏感、过期、跨 scope 内容 |
| `BudgetPacker` | 按 token 预算打包 summary/full content |
| `RecallExplainer` | 生成召回原因 |

### 3.3 检索策略

V3.3 建议使用混合检索：

| 检索方式 | 作用 |
|---|---|
| Scope filter | 先限定项目、用户、任务边界 |
| Keyword/BM25 | 捕捉文件名、模块名、错误码、明确关键词 |
| Embedding/vector | 捕捉语义相关内容 |
| Type filter | 按任务类型提升相关记忆类型权重 |

### 3.4 排序公式

初版可以使用可调权重公式：

```text
score =
  semantic_similarity * 0.40
  + keyword_match * 0.20
  + scope_score * 0.15
  + recency_score * 0.10
  + confidence_score * 0.10
  + type_weight * 0.05
```

### 3.5 上下文预算策略

| 策略 | 说明 |
|---|---|
| Summary first | 默认只注入 summary |
| Full content on demand | 只有高相关或用户要求时附 full content |
| Diversity | 避免召回多条高度重复记忆 |
| Hard filters | 排除 forgotten、敏感、跨 scope 不允许内容 |
| Budget cap | 每次召回使用固定 token 上限 |

### 3.6 召回解释

召回结果建议包含：

```json
{
  "memory_id": "mem_xxx",
  "reason": "Matched current coding task and related project decision.",
  "matched_scope": "project:scp_meat_memory_v1",
  "matched_type": "decision",
  "score": 0.86
}
```

## 5. 验收标准

| 标准 | 说明 |
|---|---|
| 能召回 | 给定 coding/debug/review 任务，能返回候选记忆 |
| 召回相关 | Top 结果与任务明显相关 |
| 召回受控 | 不会把大量无关历史塞进上下文 |
| 解释可读 | 用户能看到召回原因 |
| 安全过滤 | forgotten、敏感、过期或跨 scope 内容不会被主动召回 |
