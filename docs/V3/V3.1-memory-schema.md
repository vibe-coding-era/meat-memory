# Meat Memory V3.1 结构化记忆

状态：Planning Draft

更新时间：2026-04-13

## 1. 版本目标

V3.1 建立 V3 的统一数据基础，让后续理解、压缩、召回、关联、演进和治理都基于稳定的 Memory Schema 工作。

一句话目标：先定义清楚“记忆是什么”。

## 2. 产品方案

### 2.1 用户故事

| 角色 | 用户故事 | 价值 |
|---|---|---|
| 开发者 | 我希望项目记忆有明确类型和作用域，避免跨项目、跨任务误召回 | 提高记忆可用性 |
| Agent | 我希望知道一条记忆是事实、推测、偏好还是临时状态 | 降低误用风险 |
| 用户 | 我希望能追溯一条记忆从哪里来、什么时候写入、是否仍有效 | 增强信任与可审计性 |
| 项目维护者 | 我希望旧版本记忆可以兼容进入新模型 | 降低迁移成本 |

### 2.2 核心场景

| 场景 | 行为 |
|---|---|
| 写入项目事实 | 记录为 `fact`，作用域为 `project`，来源为 `conversation` 或 `file` |
| 写入用户偏好 | 记录为 `preference`，作用域为 `user` 或 `project` |
| 写入任务状态 | 记录为 `task_state`，作用域为 `task`，可设置过期时间 |
| 迁移旧记忆 | 缺少结构化字段时使用保守默认值，不做过度推断 |
| 查询记忆 | 支持按 scope、type、status、source、tag 过滤 |

### 2.3 功能分解

| 功能 | 说明 | 优先级 |
|---|---|---|
| Memory Schema V3 | 统一记忆对象字段 | P0 |
| Scope Model | 支持 global、user、project、branch、task、session | P0 |
| Memory Type | 支持 fact、preference、decision、task_state、summary、issue、code_context、meeting_note、hypothesis | P0 |
| Source Model | 记录 conversation、file、api、meeting、manual、system、legacy | P1 |
| Confidence Model | 标记 explicit、inferred、unverified、stale | P1 |
| Status Model | 标记 active、archived、deprecated、forgotten、needs_review | P1 |
| V2 兼容 | 旧记忆运行时适配或迁移 | P2 |

## 3. 技术方案

### 3.1 数据结构

建议 Memory V3 基础结构：

```json
{
  "id": "mem_xxx",
  "scope": {
    "level": "project",
    "scope_id": "scp_meat_memory_v1"
  },
  "type": "decision",
  "content": "V3 will use structured memory with lifecycle and source tracking.",
  "summary": "V3 memory schema adds lifecycle and source tracking.",
  "source": {
    "kind": "conversation",
    "ref": "thread_id/message_id",
    "created_by": "user"
  },
  "confidence": "explicit",
  "status": "active",
  "tags": ["v3", "schema", "memory-model"],
  "metadata": {},
  "created_at": "2026-04-13T00:00:00Z",
  "updated_at": "2026-04-13T00:00:00Z",
  "expires_at": null
}
```

### 3.2 存储设计

| 表/对象 | 说明 |
|---|---|
| `memories` | 主记忆表，保存结构化字段和正文 |
| `memory_sources` | 可选拆分表，用于保存多来源引用 |
| `memory_tags` | 可选拆分表，用于标签索引 |
| `memory_versions` | 可选预留，用于后续演进记录 |

V3.1 阶段可以先把 `source`、`tags`、`metadata` 作为 JSON 字段保存，等 V3.4/V3.5 对查询性能和审计有明确压力后再拆表。

### 3.3 API

| API | 说明 |
|---|---|
| `create_memory` | 创建 V3 结构化记忆 |
| `get_memory` | 按 id 读取记忆 |
| `update_memory` | 更新内容、摘要、标签、metadata |
| `search_memory` | 按 scope/type/status/source/tag 检索 |
| `change_status` | 修改 active、archived、deprecated、forgotten、needs_review |

### 3.4 迁移策略

| 旧数据情况 | V3 处理 |
|---|---|
| 只有正文 | `type=summary` 或 `fact`，`confidence=unverified` |
| 无来源 | `source.kind=legacy` |
| 无 scope | 进入默认 project scope 或 legacy scope |
| 无状态 | `status=active` |
| 无摘要 | `summary=null`，后续由 V3.2 补齐 |

迁移原则：宁可保守标记，也不要过度推断。

## 5. 验收标准

| 标准 | 说明 |
|---|---|
| 结构化写入 | 新记忆可按 V3 schema 写入 |
| 结构化读取 | API 返回 scope、type、source、confidence、status 等字段 |
| 作用域隔离 | search 支持按 scope 过滤 |
| 旧数据兼容 | V2 记忆不会因 V3 schema 变更不可读 |
| 状态变更 | active、archived、deprecated、forgotten、needs_review 可被更新 |
